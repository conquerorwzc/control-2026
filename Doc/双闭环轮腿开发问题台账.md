> 本文用于持续记录 `wheel_legged_demo_27` 在机构学、硬件接入、任务调度和真机调试中出现的问题。
>
> 更新规则：每个问题至少记录“现象、影响、根因、处理、验证、遗留风险”。解决后不删除，标记为“已关闭”，以免以后重复踩坑。
>
> **安全红线：** 只有明确允许“烧录 / 刷入 / 下载固件”时才能写入开发板。电机已使能或存在 PID、力矩、电流输出时，严禁通过 J-Link、GDB、断点、单步等方式暂停 MCU；紧急情况优先物理断电或经过统一安全入口发送停止命令。

**最后更新：2026 年 7 月 30 日**

## 1. 当前工程边界

| 项目 | 当前结论 |
| --- | --- |
| 工程 | `control-2026`，目标机器人为 `UserApp/robot/wheel_legged_demo_27` |
| 主控 | STM32H7 |
| 单腿机构 | 两个同心主动轴驱动的平面双闭环连杆腿 |
| 坐标系 | O 为原点，x 向右为正，y 向下为正；P 为足端 |
| 主动轴角 | phi1：x 正向转到 OA；phi2：x 正向转到 OC |
| 当前正式功能 | 读取四个关节电机反馈、链传动换算、腿部正运动学（FK） |
| 当前不做的事 | 不进行关节 PID 输出、IK 真机闭环输出、轮毂控制、平衡控制 |
| 电机安全状态 | 关节电机初始化后执行一次 `DMMotorStop()`；运行期只读反馈，不反复 Stop/Enable |

### 1.1 当前代码分层

```text
RobotTask（约 1 ms）
    ├── 更新左腿：读取两个关节反馈 → 链传动换算 → FK
    └── 更新右腿：读取两个关节反馈 → 链传动换算 → FK

纯运动学层
    └── double_closed_loop_leg.[ch]
        输入：phi1、phi2、几何参数、装配支路
        输出：A/B/C/D/E/F/P、腿长、腿角；并提供离线 IK

传动层
    └── joint_transmission.[ch]
        输入：电机累计角
        输出：主动轴角 phi1 / phi2
```

原则：纯运动学模块不包含 CAN、电机对象、FreeRTOS、PID 或硬件句柄；左右腿、电机方向、零位、链轮齿数等差异仅放在腿配置中。

| 腿 | 前关节（phi2 / OC）机械零点电机反馈 | 后关节（phi1 / OA）机械零点电机反馈 |

| 左腿 | +0.0974674225 rad | -3.34725761 rad |

## 3. 已关闭问题

### P-001：反馈读取函数反复发送 `DMMotorStop()`

| 项目 | 记录 |
| --- | --- |
| 状态 | 已关闭 |
| 现象 | 原 `WheelLeggedJointStopAndGetAngle()` 在约 1 ms 的循环内先 Stop 电机，再读取累计角。 |
| 影响 | 即使只是查看 FK，也会持续修改电机输出状态；未来接入控制器时会与 Enable、PID、力矩指令冲突。 |
| 根因 | 把“安全输出动作”和“读取反馈”放进了同一函数。 |
| 处理 | 改为 `WheelLeggedJointGetAngle()`，仅读取 `motor->measure.total_angle` 并更新 `feedback_ready`。 |
| 当前结论 | `DMMotorStop()` 只在每个关节执行 `DMMotorInit()` 后调用一次；运行期的 FK 更新不写 CAN 输出状态。 |
| 后续约束 | 任何读取、估计、FK、IK 函数都不得隐式 Stop、Enable 或发送控制量。 |

### P-002：临时 PID 测试与零力矩逻辑抢同一电机

| 项目 | 记录 |
| --- | --- |
| 状态 | 已关闭 |
| 现象 | 测试时发现一侧 PID 参考偶尔为 0，另一侧一会儿为 0、一会儿不是 0，表现像多个逻辑在抢电机。 |
| 影响 | 达妙 CAN 发送任务异步运行时，可能交替发送 Stop、Enable、PID 参考，出现无力、抖动或不可预测的转动。 |
| 根因 | 临时测试路径中存在 `Stop → Enable → SetPIDRef`，而周期性发送与状态更新并非一个唯一出口。 |
| 处理 | 删除临时 `wheel_legged_pid_test.[ch]`，移除 Leg 对象内的临时 IK/PID 真机测试状态和写电机函数。 |
| 验证 | 当前 `RobotTask()` 只更新两腿反馈与 FK，不调用 `DMMotorEnable()`、`DMMotorSetPIDRef()`。 |
| 后续约束 | 一台电机任一时刻只能由一个“输出仲裁器/控制状态机”写命令；调试逻辑不能绕过该出口直接写电机。 |

### P-003：临时 IK/PID 调试逻辑污染正式腿对象

| 项目 | 记录 |
| --- | --- |
| 状态 | 已关闭 |
| 现象 | 为了临时验证 IK 和定腿长 PID，在正式 `Leg` 对象中加入了测试状态、斜坡、参考发送等逻辑。 |
| 影响 | 正式对象职责不清；测试结束后仍可能影响运行，并增加日后调试定位成本。 |
| 根因 | “计算运动学”和“驱动真机”的边界未分开。 |
| 处理 | 删除 `WheelLeggedLegInverseKinematicsTest_t`、`inverse_kinematics_test` 及相关函数；IK 保留在纯运动学模块内。 |
| 当前结论 | FK/IK 算法可离线调用；若未来要真机验证，应建立独立、显式使能、可一键退出的测试入口。 |

### P-004：以为 Stop 是“读取电机角度”的必要步骤

| 项目 | 记录 |
| --- | --- |
| 状态 | 已关闭 |
| 现象 | 曾通过 `WheelLeggedJointStopAndGetAngle()` 获取反馈，容易误以为不 Stop 就无法读角度。 |
| 影响 | 导致正常观测路径侵入执行器状态，甚至可能每周期重复发送零力矩。 |
| 根因 | 对电机“反馈通道”和“命令通道”职责混淆。 |
| 处理 | 将函数改名为 `WheelLeggedJointGetAngle()`，代码和命名均明确其只读职责。 |
| 后续约束 | `Stop` 是控制命令，不是传感器采样动作。 |

### P-005：FK / IK 与机械装配支路、零位标定混在一起理解

| 项目 | 记录 |
| --- | --- |
| 状态 | 基本关闭，后续仍需真机复核 |
| 现象 | 足端 P 的部分坐标曾出现偏差；需要区分几何公式错误、装配支路错误、链传动方向错误和电机零位错误。 |
| 根因 | 双闭环机构同一组边长存在多种圆交点；数学支路与实际装配支路必须一致。电机反馈角也不是天然等于主动轴角。 |
| 处理 | 将圆交点支路明确写入配置；用链传动模型将电机累计角换算到 phi1、phi2；分别记录左右腿电机机械零点。 |
| 验证 | 已做 FK→IK 回代：左腿最大电机参考误差约 0.000381 rad（0.0219°），右腿误差接近 0。 |
| 后续约束 | 修改杆长、零点、齿数或装配方向后，必须重新做 FK→IK 回代和多姿态实测；不可只看单一点 P。 |

### P-006：底盘 component 逻辑误放到 robot 层

| 项目 | 记录 |
| --- | --- |
| 状态 | 已关闭 |
| 现象 | 在加入遥控命令与底盘任务时，曾将底盘对象、关节输出仲裁和 FK 调度放到 `wheel_legged_demo_27/robot.c` 附近。 |
| 影响 | 通用底盘能力会被绑死在一台车；修改左右腿 CAN、零位或杆长时容易同时改动 component 逻辑。 |
| 根因 | 未明确区分“机器人装配层”和“底盘 component 层”。 |
| 处理 | 将 `chassis.[ch]`、`chassis_leg.c`、`chassis_output.c` 移入 `components/chassis/chassis_wheel_legged_double_closed_loop`。robot 层只创建对象、初始化遥控器、传入本车配置并调度两个任务。 |
| 当前结论 | component 通过 `WheelLeggedChassisInitConfig_t` 接收配置，绝不包含任一具体机器人目录的 `robot_config.h`。 |
| 后续约束 | 与机构无关的控制、输出、安全状态机均进入 chassis component；CAN ID、零位、齿数、杆长、装配支路留在各机器人自己的 `robot_config.h`。 |

## 4. 当前风险与待解决问题

### R-001：尚未建立唯一电机输出仲裁器

当前虽然没有任何运行期电机输出，但未来接入 PID、力控、保护、调试、急停后，必须只有一个统一出口负责生成并发送关节命令。建议状态至少区分：失能、零力矩、位置测试、力矩/电流控制、故障锁定。

### R-002：轮毂、IMU、遥控器、云台尚未接入正式功能

当前 `RobotInstance` 中保留了 `gimbal`、`rc_data`，底盘中保留 `imu`，轮毂也仅保存 CAN 地址。它们不是已完成的控制链路，不能据此认为整车可运动或可平衡。

### R-003：达妙反馈有效标志的判定仍需确认

当前 `feedback_ready` 使用 `measure.state != 0u` 进行粗略判断。后续应确认达妙协议中各状态值的含义，明确哪些状态代表正常反馈、失能、故障或离线。

### R-004：尚缺少板端雅可比、力映射与平衡控制

目前完成的是腿部位置运动学基础。后续还需要：

1. 求并验证腿部雅可比：主动轴速度 → 足端速度。
2. 求转置力映射：期望足端力 → 两个关节力矩。
3. 接入 IMU、轮速、腿部状态，建立状态估计。
4. 在明确输出仲裁和保护边界后，再接入 LQR / 平衡控制。

### R-005：工程仍存在一个既有编译告警

当前已知告警为 `IMU_LeverArm_Compensation declared static but never defined`。它与本轮腿部 FK/IK 修改无直接关系，但后续应单独定位并消除，避免真正的遗漏被告警淹没。

## 5. 后续开发顺序

1. **冻结并回归验证纯机构学层**：多姿态测量 A、C、F、P，记录误差；保留每次几何或标定改动的结果。
2. **完成统一输出仲裁器**：所有 Stop、Enable、PID、力矩指令必须只从一个模块发出。
3. **建立安全测试模式**：测试模式默认失能，只有显式命令才能启用；退出、超时、反馈异常时回到零力矩或失能。
4. **接入轮毂和 IMU**：先确认 CAN 通道、反馈、方向和单位，再谈整车闭环。
5. **完成雅可比与力映射验证**：先离线数值差分，再做低风险静态真机检查。
6. **完成状态估计与平衡控制**：最后再接入腿长、腿角、轮速、姿态的闭环控制。
